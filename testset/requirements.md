# 测试集需求文档（ReqGuard 评估用）

> **规模说明**：10 条为起步规模，统计意义有限；正式评估建议扩展到 20～30 条，覆盖更多高风险类别。对外引用数字必须来自 ≥20 条测试集。
>
> **用途**：本文件只用于评估 ReqGuard 本身的漏报率，不是日常使用 skill 的依赖。用 ReqGuard 检查你自己的项目时，输入是你自己的需求文档和代码，不需要本文件。
>
> **本文件不含风险等级**：风险等级由 ReqGuard 按 `risk-rules.yaml` 自动判定，写进需求文档会让检查器被标注牵着走。
>
> **判定上下文**：检查对象为 `testset/code/` 下的 6 个 TypeScript 文件（`auth.ts`、`crypto.ts`、`payment.ts`、`permission.ts`、`order.ts`、`ui.ts`），检查范围为该目录全部文件。

---

### R-01 密钥不得以字面量形式出现在源码中

- **优先级**：MUST
- **需求原文**：所有密钥类配置必须从环境变量或配置中心读取，不得以字面量形式出现在源码与版本库中。
- **验收判据**：
  - AC-1 源码与配置文件中不存在 JWT 签名密钥、支付密钥、数据库口令的直接赋值字面量。
  - AC-2 密钥的读取路径为环境变量或配置中心；缺失时启动失败或抛出明确错误，不得静默使用默认值。
  - AC-3 不存在「读取环境变量但带写死兜底值」的写法（`process.env.X || "固定值"` 同样违规）。
- **范围**：`testset/code/` 全部文件
- **不包含**：密钥轮换、KMS 接入方式

---

### R-02 业务接口必须在服务端校验 token

- **优先级**：MUST
- **需求原文**：除登录与健康检查外的所有业务接口必须在服务端校验访问 token，不得仅依赖前端拦截。
- **验收判据**：
  - AC-1 订单创建、查询、审批、支付发起、支付回调等业务接口，其路由注册处均挂有 token 校验中间件。
  - AC-2 token 校验在服务端执行，且能定位到校验实现被路由实际引用（不是仅存在于某个文件中）。
  - AC-3 仅存在校验中间件的「定义」而没有任何路由引用时，判为未满足。
- **范围**：`order.ts` 的路由注册、`auth.ts` 的中间件实现
- **不包含**：token 加密算法选择、刷新机制

---

### R-03 密码必须使用带盐慢哈希存储

- **优先级**：MUST
- **需求原文**：用户密码必须使用 bcrypt、argon2 或 scrypt 等带盐的慢哈希存储，禁止使用 MD5、SHA1 直接哈希。
- **验收判据**：
  - AC-1 密码哈希函数使用 bcrypt / argon2 / scrypt（含每次随机盐与可调代价参数）。
  - AC-2 注册写入与登录校验使用同一慢哈希方案，代码中不存在 MD5 / SHA1 的密码路径。
  - AC-3 非密码场景（如文件摘要）使用 SHA-256 等合规算法，不计入违规。
- **范围**：`crypto.ts` 的密码哈希函数、`auth.ts` 的注册与登录
- **不包含**：密码强度校验、找回密码流程

---

### R-04 支付下单必须接入真实网关

- **优先级**：MUST
- **需求原文**：支付下单必须调用真实支付网关；mock 实现只允许在测试环境且通过显式开关启用，默认关闭。
- **验收判据**：
  - AC-1 支付下单路径中存在对真实网关 SDK 或网关 HTTP 接口的调用，并能回写网关返回的支付单号。
  - AC-2 mock 分支必须同时满足：有显式开关（环境变量或配置项）、默认关闭、生产环境不可达。
  - AC-3 返回体出现 `mock: true` 或 `MOCK-` 前缀单号，而路径中没有任何网关调用时，判为未满足。
- **范围**：`payment.ts` 的下单函数
- **不包含**：退款、对账、多币种

---

### R-05 支付回调必须验签且幂等

- **优先级**：MUST
- **需求原文**：支付回调必须校验网关签名，且同一笔回调重复到达时只入账一次（幂等）。
- **验收判据**：
  - AC-1 回调处理函数体内实际调用了签名校验，验签失败必须中止处理。
  - AC-2 入账前按订单号或回调流水号做幂等判断，重复回调不重复入账。
  - AC-3 仅有验签函数定义、回调路径未调用它，判为未满足。
- **范围**：`payment.ts` 的回调处理与验签函数
- **不包含**：回调重试策略、补单任务

---

### R-06 权限必须覆盖四类角色且服务端判断

- **优先级**：MUST
- **需求原文**：系统必须支持 admin、staff、nurse、approver 四种角色，且每种角色的可执行操作在服务端有对应的权限判断。
- **验收判据**：
  - AC-1 角色定义包含 admin、staff、nurse、approver 四项。
  - AC-2 审批动作仅 approver（或 admin）可执行，nurse 与 staff 不可执行。
  - AC-3 权限判断在服务端执行，且不存在「未命中角色时默认放行」的兜底分支。
- **范围**：`permission.ts` 的角色定义与判断函数、`order.ts` 的审批入口
- **不包含**：数据权限（行级隔离）、角色管理界面

---

### R-07 订单状态必须覆盖五态并校验迁移

- **优先级**：MUST
- **需求原文**：订单状态必须覆盖 PENDING、APPROVED、REJECTED、WITHDRAWN、EXPIRED 五种，并实现对应用状态迁移校验。
- **验收判据**：
  - AC-1 状态定义包含 PENDING、APPROVED、REJECTED、WITHDRAWN、EXPIRED 五种取值。
  - AC-2 状态迁移有显式迁移表或校验逻辑；非法迁移（如 REJECTED → APPROVED）被拒绝。
  - AC-3 撤回与超时两条路径可分别触发 WITHDRAWN 与 EXPIRED。
- **范围**：`order.ts` 的状态定义与迁移函数
- **不包含**：状态变更通知、前端状态展示

---

### R-08 订单提交必须幂等

- **优先级**：MUST
- **需求原文**：订单提交接口必须做幂等控制，同一用户重复提交同一业务标识时只能生成一笔订单。
- **验收判据**：
  - AC-1 提交接口要求携带幂等键（或业务唯一标识），并在落库时去重。
  - AC-2 重复提交返回首次结果或同一订单号，不产生第二笔订单记录。
  - AC-3 仅在前端按钮做防抖、服务端无任何控制时，判为未满足。
- **范围**：`order.ts` 的下单处理函数与其写库路径
- **不包含**：分布式锁实现细节、重复支付处理

---

### R-09 关键事件必须写入审计表

- **优先级**：MUST
- **需求原文**：登录（成功与失败）、支付发起与回调、审批通过与驳回六类事件必须写入审计表，记录操作人、操作对象与结果。
- **验收判据**：
  - AC-1 上述六类事件各有一条审计写入调用，写入持久化存储（表或文件），而非仅输出到 stdout。
  - AC-2 每条审计记录包含操作人、操作对象、结果、时间四项。
  - AC-3 仅有 `console.log` 输出时，判为未满足。
- **范围**：`auth.ts` 登录、`payment.ts` 支付发起与回调、`order.ts` 审批
- **不包含**：审计日志的不可篡改性、日志归档策略

---

### R-10 界面文案应支持国际化

- **优先级**：MAY
- **需求原文**：界面文案应支持国际化，不得将展示文案硬编码在组件中。
- **验收判据**：
  - AC-1 展示文案通过文案 key 取用（如 `t("order.status.pending")`），并存在对应词条表。
  - AC-2 组件内不存在硬编码的中文或英文展示文本。
- **范围**：`ui.ts`
- **不包含**：翻译质量、多语言切换入口、日期与货币本地化
