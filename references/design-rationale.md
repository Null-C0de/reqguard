# 设计原理：ReqGuard 为什么这样写

> 本文解释 ReqGuard 的机制设计，供想深入理解或要修改 skill 的人查阅。README 只放链接，不展开。

---

## 1. Skill 是什么，不是什么

**不是模型**：没有训练、没有微调、没有权重。换模型后行为会变。

**不是传统程序**：没有确定性执行路径，同一条输入两次跑可能给出不同措辞的结论。

**是**：一份注入到 agent 上下文里的**结构化约束集**。它不增加模型的知识，它改变模型的**推理路径**与**输出形态**：

| 维度 | 无 skill（自由对比） | 有 ReqGuard |
| --- | --- | --- |
| 检查粒度 | 整篇需求 vs 整个仓库 | 一条判据 vs 一处证据 |
| 停止条件 | "看起来都对上了" | 每条 MUST 都有结论且"符合"必须带 E1 证据 |
| 结论形态 | 段落式叙述 | 三态判定 + 三元证据 + 固定九节结构 |
| 缺证据时 | 倾向于推断"应该实现了" | 必须判"无法判定"并写卡点 |
| 判据来源 | 模型自己总结的"合理要求" | 需求原文逐字抽取，禁止自编 |
| 风险权重 | 平铺，或按模型直觉 | 规则文件分级，高风险置顶且强制举证 |

一句话：**它把"自由对比"变成"逐条举证"**，把隐性判断标准变成可复核的显性产物。

## 2. 四个作用点

### 2.1 角色锚定（Role anchoring）

开头明确"你是严格的需求覆盖检查器"，并同时给出**否定的身份清单**（不是代码质量评审、不是架构顾问、不是需求作者、不是测试执行者）。

为什么需要否定清单：LLM 在被要求"检查代码"时，默认会滑向它训练分布里最高频的两种任务——代码 review 与重构建议。这两种输出看起来专业，却会**挤占**覆盖检查的注意力预算，还会让读者误以为"没提需求 = 需求没问题"。

否定清单是廉价的边界设施：一句话的成本，换掉整类跑题输出。

### 2.2 强制输出结构（Structural forcing）

报告固定九节，顺序固定，明细表列固定，且规定"一条 MUST 一行，判符合的也要出现"。

三个作用：

1. **让漏项可见**：漏掉一条 MUST，明细表就少一行，评审者可以直接数。自由叙述里，漏项是隐形的——你无法从一段流畅的总结里看出它没提第 7 条需求。
2. **让"通过"变贵**：要写"符合"，必须填证据列。填不出来就暴露了。结构本身构成一种成本约束。
3. **让结果可比**：固定结构才能做批量评分（`run_eval.py` 靠结构解析），否则每次输出形态不同，无法统计。

### 2.3 硬约束与禁止项（Hard constraints & prohibitions）

H1–H9 是不能协商的条款，其中三条直接对应本 skill 要解决的具体失效：

- **H1 高风险禁止只写"已覆盖"**：删掉"看起来没问题"这个措辞出口。
- **H2 找不到证据一律判"无法判定"，不得判"符合"**：把"没查"和"查了没问题"分开。
- **H3 `mock/hardcode/stub/TODO` 命中必须标记"疑似本地实现，需人工确认"**：把最难自动判定的一类（本地能跑、线上不成立）转成人工确认项，而不是猜测。

另有 H6 反向约束：**不得把"无法判定"当默认结论回避判定**。只加 H2 不加 H6，会诱导模型走向另一个极端——全判"无法判定"，指标看起来"没有漏报"，实际没交付任何结论。一对互相拉扯的约束，才把行为压在中间。

禁止清单（第 8 节）列出的是**已知的退化写法**，例如"建议后续补充 token 校验"——把"不符合"写成建议，是覆盖检查里最隐蔽的漏报形态：结论被降级成 TODO，读者以为可以放行。

### 2.4 外部化判据（Externalized criteria）

两处判据被移到模型之外：

**（一）合格判据来自需求原文，且必须标注出处片段。** 模型擅长"补全一个合理的验收标准"，而这恰恰是漏报的温床：自编的判据往往比真实要求宽松（模型会挑容易验证的版本），检查通过的就是那条被放宽的判据。要求摘录原文，等于强制它对着原句判。

**（二）风险分级交给 `risk-rules.yaml`。** 为什么不让模型直接判风险等级？

- 风险等级决定"是否阻断发布"，属于业务决策，不应由每次推理临时决定；
- 规则文件可被团队 review、diff、覆盖，模型的直觉不行；
- 同一份需求在不同时间跑，分级必须稳定，否则结果不可复现。

代价是关键词规则会有误判（召回优先的粗筛）。这是明确的设计取舍：**宁可把中风险误升为高风险（多花人工），不可把高风险漏降为中风险（放行事故）**。规则判不了的一律进"待人工定级"，不硬猜——"猜"在这里是最坏的选项，因为它把不确定性伪装成了结论。

## 3. 为什么"强制证据定位"能堵住"本地能跑即合规"

### 3.1 失效的机理

"本地能跑即合规"不是懒惰，是**捷径**：运行结果是一个强信号，且获取成本极低（跑一下就知道），而"需求是否被真正满足"需要跨文件追调用链、读配置、看开关默认值，成本高一个数量级。在成本压力下，任何检查者（人也是）都会向强信号收敛。

这类失效的共同结构是：**代码里存在实现痕迹，但实现不在生效路径上**。典型四种：

| 形态 | 例子 |
| --- | --- |
| 硬编码替代配置 | `const JWT_SECRET = "dev-secret"` |
| 定义但未挂载 | 写了 `requireAuth` 中间件，路由上没挂 |
| mock 替代真实依赖 | `return { success: true, mock: true }` |
| 降级实现未收口 | `NODE_ENV !== "production"` 分支在生产同样可达 |

这四种形态在运行时都**不报错**，甚至行为正确——所以运行结果无法区分它们。

### 3.2 证据定位如何切断捷径

ReqGuard 把"符合"的门槛从"我认为实现了"改成"我能指出在哪一行、哪个函数、哪段代码让它生效"。这个改动切断了捷径的三条腿：

**（1）把不可验证的断言变成可被反驳的断言。**
"已覆盖"无法被反驳；`config/jwt.ts :: const JWT_SECRET :: "dev-secret-123"` 可以被任何人打开文件核对。**可反驳性是漏报的天敌**——漏报之所以能存活，靠的就是结论不可反驳。

**（2）E1 / E2 / E3 证据分级，直接命中"定义 ≠ 生效"。**
- E1（直接证据）= 代码在真实执行路径上做了这件事；
- E2（间接证据）= 只说明意图（注释、README、未被调用的函数）；
- E3 = 找不到。

规则是**只有 E1 能支撑"符合"**。这一条恰好封死了上表四种形态：它们全部只能提供 E2——实现痕迹存在，但不在生效路径上。要让 E2 变成 E1，检查者必须追调用链（步骤 4.3），而追调用链正是原本被省略的高成本动作。

**（3）把"没查"和"查了没问题"分成两个结论。**
"无法判定"必须写卡点（缺哪个文件、断在哪条调用链）。这使"跳过检查"不能伪装成"检查通过"——自由叙述里两者都是一句"未发现问题"。

### 3.3 一个反例说明为什么行号只作辅助

如果证据要求是"给出行号"，模型可以给出一个看起来精确的行号（甚至编造），而读者很难核验；一旦代码改动，行号全部漂移，历史报告立刻失效。

改用 `文件 :: 函数 :: 片段`：
- 函数名与代码片段是**语义锚点**，跨提交稳定；
- 片段可以在仓库里直接 grep，核验成本极低；
- 编造片段的成本远高于编造行号（片段要"像真的"，就得读过代码）。

**让证据的伪造成本高于取证成本**，是这套约束能长期生效的经济学原因。

## 4. 设计取舍记录

| 取舍 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 只处理 MUST | 主流程只判 MUST，SHOULD/MAY 单列 | MUST 决定能否验收，混算会稀释信号 | 需要需求方正确标注优先级 |
| 三态而非两态 | 增加"无法判定" | 两态制会强迫模型在证据不足时二选一，产生系统性漏报 | 出现"无法判定率高"的失效模式，需人工介入 |
| 风险分级外置 | YAML 规则 | 可 review、可 diff、结果可复现 | 关键词粗筛，有误升级 |
| 判据原文锚定 | 必须摘录出处片段 | 阻断"自编宽松判据" | 需求写得含糊时只能进"待人工定级" |
| 报告结构固定 | 九节 + 固定列 | 漏项可视化、结果可解析 | 报告偏长，不适合快速一瞥 |
| 不生成修复代码 | 只给方向 | 修复方案是另一个任务，混进来会稀释判定 | 用户需要自己改 |
| 规则覆盖而非 fork | `risk-rules.local.yaml` | 团队自定义不必改 skill 本体 | 需要维护规则文件 |

## 5. 已知失效模式（什么时候它不灵）

1. **无法判定率过高**：说明检索能力或范围界定出问题（代码不可读、仓库太大、需求太含糊）。此时指标"好看"是假象，必须看无法判定率。
2. **需求文档本身不可判定**：判据含糊（"密码要安全"）时，skill 只能把它送进"待人工定级"。这不是 skill 的失败，是输入的失败——`references/requirement-template.md` 就是为这个写的。
3. **证据可读性受限**：只有截图、压缩包未展开、私有依赖不可读时，拿不到 E1。
4. **模型能力不足**：追调用链需要跨文件推理，小模型容易停在 E2 就下结论。这是评估必须绑定具体模型与参数的原因（见 `references/eval-protocol.md` 第 7 节）。
5. **被"讨好"倾向污染**：模型倾向于给出"都满足了"的安慰性结论。H1/H2/H4/H6 与禁止清单都是对抗这一倾向的护栏；但它们降低概率，不消除。

## 6. 如果要改这个 skill

改动前先回答三个问题：

1. **它改变的是推理路径，还是只是措辞？** 只改措辞的改动没有价值（还可能让输出更长更难读）。
2. **它会不会给"漏报"开一个新的措辞出口？** 任何允许"没有证据也能说符合"的改动都必须拒绝。
3. **它会不会让 A/B 对比失真？** 若改动只影响 B 组提示词而非判定机制，说明你在做提示词工程，不是在做 skill。

对应地，任何修改都必须同步检查：`risk-rules.yaml` 的规则 id 是否仍被引用、`references/report-template.md` 的章节是否仍然一致、`scripts/run_eval.py` 的解析是否仍然成立。
