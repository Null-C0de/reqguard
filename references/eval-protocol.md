# 评估协议：ReqGuard 漏报率 A/B 对比

> 本协议定义「如何证明 ReqGuard 有效」，供 `scripts/run_eval.py` 与后续评估复用。
>
> 两条硬规则：
> 1. **对外引用的数字必须来自 ≥20 条测试集**；10 条仅用于跑通流程与验证报告结构。
> 2. **A 组提示词必须是"正常人会写的体面提示词"**，禁止为了凸显效果而弱化 A 组。

---

## 1. 目的与边界

**目的**：度量 ReqGuard 是否降低了「需求覆盖检查」的漏报率，而不只是产出了更长的报告。

**不度量**：代码质量、修复建议质量、token 成本以外的工程指标。

**边界**：本协议只评估 skill 本身。使用者用 ReqGuard 检查自己的项目时，**不需要**跑本协议，也不需要使用 `testset/`、不需要写 `ground-truth`。

---

## 2. 实验设计

| 项 | 设置 |
| --- | --- |
| 自变量 | 是否加载 `SKILL.md`（A 组不加载 / B 组加载） |
| 控制变量 | 同一份需求文档、同一份代码快照、同一个模型与参数、同一宿主、同一检查范围 |
| 每组重复 | 3 次，每次**全新 session**（不得复用上下文、不得保留上一轮结论） |
| 采样位置 | 模型输出即结果，不做人工润色；3 次取中位数，并附全部 3 次原始明细 |
| 盲评 | 评分人不知道结果属于 A 组还是 B 组（输出先脱敏再评分） |
| 记录物 | `eval_output/<timestamp>/{A1,A2,A3,B1,B2,B3}.md` + `score.md` |

### 2.1 A 组提示词（体面版，逐字使用）

```text
你是一名负责交付验收的资深工程师。请对照需求文档，逐条检查代码仓库的实现情况。

要求：
1. 以需求文档为准，逐条核对每条需求是否被代码实现满足；MUST 条款必须全部覆盖，SHOULD / MAY 可以简要列出。
2. 对每条需求给出明确结论：已满足 / 未满足 / 无法判断，并说明理由。
3. 对"未满足"的条目，指出对应的代码位置（文件、函数或关键代码片段），说明具体缺少什么。
4. 对"已满足"的条目，说明是哪段实现支撑了这个结论。
5. 判断时不要只依据代码能否运行或测试是否通过，请结合配置、开关与实际调用链确认实现是否真的生效。
6. 最后输出一张汇总表，列出所有"未满足"和"无法判断"的条目，供我决定这次交付是否可以验收。
```

**为什么这样写，而不是一句话版**：

- 一句话版（"帮我看看需求都实现了吗"）测的是模型会不会主动做结构化检查，噪声极大，且不能代表真实交付场景；
- 本版是真实工程师会写的提示词：有范围、有逐条要求、有证据要求、有汇总要求。它能拿到不错的基线（这正是它的价值——**A 组越强，B 组的提升才可信**）；
- 本版**刻意不包含** ReqGuard 的机制：不要求风险分级、不要求三元证据、不要求 `mock/hardcode` 扫描、不定义"无法判定"的纪律。这些是 skill 的增量，不是基线的一部分。

**A 组维护规则**

- A 组提示词属于评估基准的一部分，**修改必须走 PR 并说明理由**，且新旧结果不可直接比较（需重跑）；
- 禁止出现"敷衍版""弱化版"A 组。评审时如果发现 A 组被削弱，本次结果作废；
- 禁止在 A 组里夹带 ReqGuard 的具体约束（例如"请按风险等级排序""必须给出文件::函数::片段"）。

### 2.2 B 组提示词（加载 SKILL.md 后的调用指令）

```text
已加载 ReqGuard 的 SKILL.md 与 risk-rules.yaml。请对以下输入执行需求覆盖检查：

- 需求文档：testset/requirements.md
- 代码：testset/code/
- 风险规则：risk-rules.yaml（默认）
- 检查范围：testset/code/ 全部文件

请严格按 SKILL.md 第 3 节工作流执行，并按第 6 节报告结构输出，不要跳过任何 MUST 条款。
```

B 组提示词**只提供输入与入口**，不追加任何额外判定提示——额外提示会把 B 组变成"提示词工程"而非"skill 效果"。

## 3. 指标定义

记：

- `N_gold_neg` = ground-truth 中 `expected=不符合` 的条目数
- `N_gold_pos` = ground-truth 中 `expected=符合` 的条目数
- `N_must` = ground-truth 中 `priority=MUST` 的条目数

### 3.1 漏报率（主指标）

```
漏报率（主口径） = |{expected=不符合 且 actual=符合}| / N_gold_neg
漏报率（严格口径） = |{expected=不符合 且 actual ∈ {符合, 无法判定, 未列出}}| / N_gold_neg
```

- **主口径**回答"有多少坑被明确放过了"；
- **严格口径**额外把"无法判定"和"根本没提"算作漏报，用于防刷分；
- 报告须同时给出两个数；对外引用统一用**严格口径**，因为它更难被"一律无法判定"策略刷高。

### 3.2 误报率

```
误报率 = |{expected=符合 且 actual=不符合}| / N_gold_pos
```

- 只统计 ground-truth 中"应当符合"的样本；
- `expected=符合` 但被判"无法判定"的，**不计入误报**，计入无法判定率（它不冤枉好人，但也没交付结论）。

### 3.3 无法判定率

```
无法判定率 = |{actual=无法判定}| / N_must
```

- 分母是 MUST 条目总数（含期望符合与期望不符合的样本）；
- **单独报告，且不得用它冒充成绩**：无法判定率高说明 skill 在该场景失效，不等于漏报率低；
- 若"严格漏报率低而无法判定率高"，结论必须写成"**未发现问题，但没有交付结论**"，不得写成"通过"。

### 3.4 证据定位准确率

```
证据定位准确率 = |{判定=不符合 且 证据命中 gold.code_location}| / |{判定=不符合}|
```

命中判定规则（避免行号漂移导致的误判）：

1. 给出 `文件`，且
2. 给出 `函数名`（命中 ground-truth 的 `function` 字段，允许大小写差异与括号差异），且
3. 片段中命中 `match_tokens` 至少 1 个；
4. **行号不参与命中判定**，只作为辅助信息记录（行号错但函数与片段对的，仍算命中）。

判"不符合"但完全没给证据的，计为未命中。

### 3.5 汇总表格式

| 组别 | 漏报率（主） | 漏报率（严格） | 误报率 | 无法判定率 | 证据定位准确率 | 备注 |
| --- | --- | --- | --- | --- | --- | --- |
| A（中位数） | | | | | | |
| B（中位数） | | | | | | |
| 差值（B−A） | | | | | | 负值表示 B 更好 |

## 4. 统计口径（必须写清，否则数字不可比）

1. **主指标分母只算 MUST**。SHOULD / MAY 单独出表，不进入四项主指标——它们不阻断验收，混算会稀释信号。
2. **判定三态归一化**：`符合 / 已满足 / 满足` → `符合`；`不符合 / 未满足 / 缺失` → `不符合`；`无法判定 / 无法判断 / 不确定` → `无法判定`。
3. **模糊结论归为未匹配**："基本符合""部分符合""大体满足"一律不算 `符合`（否则漏报会被措辞掩盖）。
4. **报告中未出现的 MUST 条款**：记为 `未列出`，在主口径下不计入漏报，在严格口径下**计入漏报**。
5. **同一需求被报告拆成多条**：合并为一条判定；只要任一子项为"不符合"，该需求记 `不符合`（与 ReqGuard 的逐条拆分规则一致）。
6. **无法判定的归类**：不进入误报分母；进入无法判定率分子；在严格漏报率中计为漏报。
7. **统计单位是"需求条目"**，不是"句子"或"代码行"。
8. **样本去重**：一条样本只被计分一次，重复出现在报告不同章节的按一次算（取最严格判定）。

## 5. 执行流程

```text
1. 冻结代码快照与需求文档（记录 commit / 文件哈希）
2. 确认 ground-truth 状态为 human-confirmed；若为 draft，结果只能内部参考，不得对外引用
3. A 组：全新 session × 3，只贴 A 提示词 + 需求文档 + 代码
4. B 组：全新 session × 3，加载 SKILL.md 与 risk-rules.yaml，贴 B 提示词
5. 脱敏：删除输出中的组别标识与 skill 痕迹
6. 评分：按第 3、4 节逐条打分，写入 eval_output/<ts>/score.md
7. 汇总：中位数入表，原始明细留档
8. 更新 results.md（仅当 ≥20 条样本时才可作为对外数字）
```

脚本化执行见 `scripts/run_eval.py`：它**不代跑模型**，只提供 `--check`（物料校验）、`--self-test`（解析器自检）、`--score <run_dir>`（对人工按本协议产出的 A/B 报告计分）。A/B 提示词以本文件原文为准，脚本不硬编码任何提示词变体，评分也不依赖提示词文本。

## 6. 样本规模与扩展

| 规模 | 用途 | 可否对外引用 |
| --- | --- | --- |
| 10 条（当前 v0） | 跑通流程、校验报告结构、发现明显缺陷 | **不可** |
| 20～30 条 | 正式评估 | 可以，需注明样本数与确认状态 |
| >30 条 | 分场景（支付/医疗/多租户）分别统计 | 可以 |

**10 条样本的已知局限**（当前 `testset/` 恰好踩中）：

- 缺少「合规的 MUST 对照样本」→ MUST 维度上的误报率无法被有效度量；
- 单一技术栈（TypeScript）→ 无法说明跨语言泛化能力；
- 风险类别覆盖偏支付/权限，缺数据隔离、并发、超时重试的高风险样本。

扩展时必须补齐以上三项，单次新增不少于 5 条，`ground-truth` 由**人**确认（AI 只能出草案）。

---

## 7. 反作弊与记录要求

- **禁止**为了让 B 组好看而修改 `ground-truth` 的 `expected`；发现标注错误须单独提交修正 PR 并重跑全部结果。
- **禁止**只报 3 次里最好的一次；必须报中位数并附全部明细。
- **禁止**在 A 组结果里做人工"补刀"（例如看完 A 组输出再手工补上漏项）。
- **禁止**用"一律无法判定"策略压低主口径漏报率——严格口径与无法判定率会同时暴露这种策略。
- 原始输出必须留档在 `eval_output/`（已在 `.gitignore` 中忽略），`results.md` 只放汇总与结论。
- 评估用的模型、参数、宿主版本必须记入 `results.md`，否则结果不可复现。
