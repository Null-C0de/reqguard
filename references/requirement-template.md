# 需求文档模板（交给 ReqGuard 检查的输入）

> 用途：ReqGuard 的检查质量**首先取决于需求文档能不能被判定**。本模板给出"可被判定"的最小结构：编号、优先级、需求原文、验收判据。
>
> 只需要复制下面的结构填写你自己的需求。不需要使用本项目的 `testset/`。

---

## 1. 单条需求的结构

````markdown
### R-01 密钥不得出现在源码中

- **优先级**：MUST
- **需求原文**：所有密钥类配置（JWT 签名密钥、第三方支付密钥、数据库口令）必须从环境变量或配置中心读取，不得以字面量形式出现在源码与版本库中。
- **验收判据**：
  - AC-1 源码与配置文件中不存在直接赋值的密钥字面量。
  - AC-2 密钥的读取路径为环境变量或配置中心，且缺失时启动失败或明确报错。
- **范围**：`src/`、`config/`、`.env.example`
- **不包含**：密钥轮换策略、KMS 接入方式（由另一条需求约定）
````

### 字段说明

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| 编号 | 是 | `R-01` 形式，全局唯一、不复用。补需求用 `R-01a`，不要重排已有编号 |
| 标题 | 是 | 一句话说清"要求什么"，不写实现方式 |
| 优先级 | 是 | `MUST` / `SHOULD` / `MAY`，定义见第 2 节 |
| 需求原文 | 是 | 一句话，必须**内含可验证的判据**（数量、枚举、禁止项、必须项） |
| 验收判据 | 是（2～3 条） | 逐条可判定的命题，能被代码或配置验证 |
| 范围 | 建议 | 哪些目录/文件/接口适用，避免判定时把无关代码算进来 |
| 不包含 | 建议 | 明确排除项，防止检查器自行扩张需求 |

> **重要**：需求文档里**不要写风险等级**。风险等级由 ReqGuard 按 `risk-rules.yaml` 自动判定——写进文档会让检查器被"标注"牵着走，也会让评估结果失真。

---

## 2. 优先级定义

| 优先级 | 含义 | ReqGuard 如何处理 |
| --- | --- | --- |
| `MUST` | 不满足则**不能验收**，构成阻断 | 逐条进入主检查流程，一条不许跳过 |
| `SHOULD` | 不满足可以验收，但必须记录并给出理由 | 单列清单，给状态，不计入"未通过" |
| `MAY` | 可选能力，做了加分 | 单列清单，给状态 |

一条需求只能有一个优先级。如果同一句里既有 MUST 又有 MAY，**拆成两条**。

---

## 3. 写作规则（决定能不能查出问题）

### 3.1 判据必须可判定

每条判据必须是**能被回答 是/否** 的命题。

| 反例（不可判定） | 改写成（可判定） |
| --- | --- |
| 密码存储要安全 | 密码必须使用 bcrypt / argon2 / scrypt 之一，且带随机盐；禁止 MD5、SHA1 直接哈希 |
| 接口要有鉴权 | 除 `/login`、`/health` 外的所有 `/api/**` 路由必须挂载服务端 token 校验中间件 |
| 支付要接入真实网关 | 下单接口必须调用真实网关 SDK；`mock` 实现仅在 `PAYMENT_MOCK=true` 且 `NODE_ENV!==production` 时可用 |
| 日志要完整 | 登录成功/失败、支付发起/回调、审批通过/驳回 6 个事件必须写入审计表，含操作人、对象、结果 |
| 支持多种角色 | 必须支持 `admin`、`staff`、`nurse`、`approver` 四种角色，且每种角色的可执行操作在代码中有对应判断 |

### 3.2 禁止出现的词

以下词会让判据失效（出现即要求改写）：

> 良好、合理、友好、优雅、高效、尽快、适当、必要时、尽可能、等等、若干、类似、基本、大致、完善、健壮

### 3.3 一条判据一件事

```
❌ AC-1 必须校验 token 并且记录审计日志
✅ AC-1 必须校验 token
✅ AC-2 必须记录审计日志
```

一条判据混了两件事时，检查器只能给出一个合并判定，漏掉其中一半的风险会直接翻倍。

### 3.4 只写"要求什么"和"怎么算通过"

需求文档**不写实现方案**（不指定框架、不指定表结构、不给代码片段）。写了实现方案，等于把"是否满足"退化成"是否照着我的写法写"，评估会失真。

```
❌ 用 jsonwebtoken 的 verify() 在 middleware/auth.ts 里实现校验
✅ 所有业务接口必须在服务端校验 token 的有效性与签名
```

### 3.5 判据要与代码可对照

判据里尽量出现**能在代码里检索到的锚点**：角色名、状态名、函数职责、配置键、接口路径、事件名。

```
✅ 订单状态必须覆盖 PENDING / APPROVED / REJECTED / WITHDRAWN / EXPIRED
   （代码里能搜到这 5 个枚举值，也能搜到 5 条迁移分支）
```

---

## 4. 编号与拆分规则

- 编号连续、不复用；删除的需求保留编号并标 `（已废弃）`，不要重排。
- 一条需求含多个独立要求 → 拆成 `R-01a`、`R-01b`，各自带判据。
- 跨模块的需求（例如"鉴权 + 审计"）→ 拆成两条，分别给范围。
- 需求变更时新增编号（`R-01` → `R-11` 取代），不要原地改写已验收过的判据。

## 5. 可直接复制的骨架

```markdown
# 需求文档：〈项目名〉〈版本号〉

> 编写人：〈姓名〉 ｜ 更新日期：〈YYYY-MM-DD〉 ｜ 适用代码版本：〈commit / tag〉

## 1. 范围
- 本次验收覆盖：〈目录 / 模块 / 接口〉
- 明确不覆盖：〈模块〉

## 2. 需求清单

### R-01 〈标题〉
- **优先级**：MUST
- **需求原文**：〈一句话，含可验证判据〉
- **验收判据**：
  - AC-1 〈可判定命题〉
  - AC-2 〈可判定命题〉
- **范围**：〈路径 / 接口〉
- **不包含**：〈排除项〉

### R-02 〈标题〉
- **优先级**：SHOULD
- **需求原文**：〈…〉
- **验收判据**：
  - AC-1 〈…〉

## 3. 术语表
| 术语 | 含义 |
| --- | --- |
| 〈角色名〉 | 〈定义，与代码中的角色标识对应〉 |
| 〈状态名〉 | 〈定义，与代码中的状态枚举对应〉 |
```

## 6. 提交前自检

- [ ] 每条都有编号、优先级、需求原文、2～3 条判据？
- [ ] 每条判据都能回答 是/否，且没有出现第 3.2 节的禁用词？
- [ ] 没有写实现方案、框架选型、代码片段？
- [ ] 没有写风险等级（交给 ReqGuard 自动分级）？
- [ ] 角色名、状态名、接口路径与代码中的实际标识一致？
- [ ] MUST 条款是否都是"不满足就不能验收"的？有没有把 SHOULD 误标成 MUST？
- [ ] 范围和"不包含"是否写清，避免检查器把无关代码算进来？
